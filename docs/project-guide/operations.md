# Запуск и эксплуатация

## Локальное окружение

Требуются Node.js от 20.19, pnpm 11 и Docker Compose v2. В package.json закреплен pnpm 11.25.0. Предпочтительно использовать поддерживаемую версию Node.js, совместимую с проектом, и одинаковый runtime в CI и на сервере.

```bash
pnpm install
pnpm infra:up
pnpm setup:dev
pnpm db:migrate
pnpm db:seed
pnpm dev
```

`setup:dev` создает недостающие приватные настройки. `db:migrate` применяет миграции пяти сервисов, `db:seed` создает локального администратора и демонстрационный каталог. Seed предназначен для разработки. Для рабочего каталога нужны собственные товары, фотографии, цены и начальные остатки.

`pnpm dev` использует порт 3000. В нашей сессии другой проект занимал этот порт, поэтому web запускался на 3001. Чтобы повторить такой запуск после `pnpm build`, запустите backend и web в двух терминалах.

```bash
CORS_ORIGIN=http://localhost:3001 WEB_URL=http://localhost:3001 pnpm --filter '!@tea/web' --parallel start
```

```bash
pnpm --filter @tea/web exec next start --hostname 127.0.0.1 --port 3001
```

Фильтр исключает web из backend-команды. Сервисы по умолчанию читают свои `.env`. Не запускайте повторный экземпляр на уже занятом порту. Для остановки нажмите Ctrl+C в соответствующем терминале. `pnpm infra:down` останавливает инфраструктуру без явного удаления Docker volumes. Перед удалением volumes проверьте резервные копии.

`pnpm health` проверяет liveness по 3000 и 4000–4005; при работе витрины на 3001 ее `/health` проверяется отдельно. Health подтверждает живой HTTP-процесс и не является полноценной проверкой доступности БД, брокера, SMTP и LiqPay.

Не публикуйте содержимое `.env`, дампы БД, bearer links и SMTP credentials в Git или скриншотах. NEXT_PUBLIC переменные встраиваются в frontend bundle, поэтому изменение обычно требует сборки web.

## Аутентификация и приватность

Пароль хранится как Argon2id hash. Access JWT имеет срок 15 минут. Refresh token случайный, БД хранит его hash и family ID. Cookie tea_access использует HttpOnly и путь `/`, tea_refresh — `/api/v1/auth`; SameSite=lax и Secure в production. Обновление refresh сериализуется и обнаруживает повтор использованного token.

Gateway валидирует подпись и роль из access JWT. Middleware страницы админки запрашивает актуальный профиль, а UI проверяет роль. При прямом вызове административного бизнес API решение опирается на JWT claims и RPC context. Уже выданный token может сохранять оставшийся срок после отзыва refresh или изменения роли. Немедленный общий отзыв API-доступа потребует дополнительной серверной проверки сессии/пользователя. UI middleware не заменяет HTTP guards.

Гость получает длинный случайный bearer token заказа, а БД хранит его hash и nonce для воспроизводимого приватного доступа. Номер заказа один не дает разрешения. Аккаунт читает только собственные заказы. История гостя привязывается после подтверждения email через UserEmailVerified и локальную VerifiedIdentity projection. Email в форме входа или совпадение строки email этого разрешения не дает.

Запросы изменяющих операций проверяются на trusted Origin. Public webhook принимает внешнее сообщение по отдельной границе и проверяет криптографическую подпись. Валидация DTO, Zod и параметризованный SQL ограничивают вход, но права на чтение и изменение сущности все равно проверяются отдельно.

## Деплой

Рабочий full-stack инстанс требует web, gateway, пяти сервисов, PostgreSQL с пятью БД, RabbitMQ, SMTP и постоянного диска для медиа. Redis уже предусмотрен Compose, но серверный каталог от него сейчас не зависит. Можно собрать приложения в CI, а на сервере запускать готовую сборку, чтобы не расходовать память VPS на build.

Для публичного окружения нужен reverse proxy с HTTPS к web/gateway. Внешний доступ к БД, management RabbitMQ и внутренним health-портам ограничивается сетью сервера. Укажите публичные origin в конфигурации, примените миграции и проверьте cookies, CORS, приватные ссылки, callback и почтовый домен.

`infra/docker-compose.dev.yml` предназначен для разработки. Его имена, локальные credentials и exposed ports не следует считать готовой production-конфигурацией. Схема развертывания и секреты конкретного VPS зависят от выбранного хостинга. Публичное окружение пока не принято.

Для Vercel можно разместить Next.js, но текущий каталог все равно обращается к gateway. Полное демо также требует постоянно работающих NestJS consumers, БД и брокера. Сам импорт apps/web на Vercel эти зависимости не поднимает.

## Наблюдаемость и восстановление

Логи используют структурированный формат и correlation ID. Сначала найдите HTTP-запрос, затем его RPC и event chain. Raw payment payload, контакты и ключи нельзя копировать в публичные журналы. Для эксплуатации полезно наблюдать возраст старейшего неопубликованного Outbox, глубину очередей и DLQ, задержку SMTP, FAILED/REVIEW_REQUIRED записи и время ответа RPC.

| Симптом                          | Где смотреть                                         | Действие                                                                              |
| -------------------------------- | ---------------------------------------------------- | ------------------------------------------------------------------------------------- |
| Заказ долго PENDING              | orders Outbox, catalog consumer, резерв              | Восстановить БД/брокер/consumer, проверить expiration; не править статус без проверки |
| PAID у провайдера, ожидание в UI | payment audit, ledger, Outbox, orders consumer       | Дождаться/запросить reconciliation и проверить доставку события                       |
| Письма не пришли                 | SMTP конфигурация, очередь notices, Mailpit локально | Проверить получателя и статус SENT/FAILED; SENT означает прием SMTP                   |
| Очередь DLQ растет               | Причина невалидного контракта или повторных ошибок   | Исправить обработчик/данные и отдельно контролировать переотправку                    |
| Refund REVIEW_REQUIRED           | Ledger и ответ провайдера                            | Ручная сверка у провайдера перед любым новым финансовым запросом                      |
| Неверный каталог после деплоя    | INTERNAL_API_URL, публичный API, версия build        | Проверить API origin и пересобрать web при изменении NEXT_PUBLIC                      |

Outbox publisher повторяет публикацию с exponential backoff, capped at 5 минут. Активные событийные consumers имеют retry/DLQ топологию, описанную в [event catalog](../architecture/events.md). Повторять нужно через совместимый обработчик, который сохраняет event ID и semantic idempotency. Простое удаление processed_events для «повторения» может повторить бизнес-эффект.

SMTP notices используют leases и bounded retries. Три неудачных попытки завершаются FAILED; после crash отправка может повториться, даже если SMTP уже принял письмо. Автоматический rollback платежа из-за ошибки SMTP не нужен: бизнес-состояние и доставка уведомления имеют разные жизненные циклы.

## Бэкапы и откат

Храните резервные копии пяти БД, медиа и приватной конфигурации, шифруйте их и регулярно проверяйте восстановление в отдельном окружении. Broker topology восстанавливается приложениями, но состояние очередей и неопубликованный Outbox требуют согласованного плана восстановления. Потеря очереди после фиксации publishedAt может потерять событие без специального восстановления.

В репозитории нет принятой production-процедуры backup/restore с измеренными RPO/RTO. Для эксплуатации нужно выбрать расписание, внешнее хранилище и выполнить пробное восстановление. Простого наличия Docker volume для защиты от потери сервера недостаточно.

Изменения БД выполняйте через Prisma Migrate. Для совместимого обновления сначала выпускайте consumers, понимающие старый и новый контракт, затем producers. Откат контейнера не отменяет примененную миграцию. Используйте forward fix или проверенную обратную миграцию с backup; данные рабочего заказа нельзя терять ради совпадения версии приложения.

## Проверка перед открытием продаж

Пройдите гостевой и авторизованный заказ, повтор одинакового запроса, отказ наличия, смену цены, резерв, отмену, отгрузку и завершение. Для почты проверьте реальное получение писем покупателем и владельцем и правильность публичных ссылок. Для LiqPay пройдите sandbox checkout/callback/status с аккаунтом мерчанта, затем отдельно live acceptance. Внесите рабочие данные продавца, тексты и реальные товары.

Кодовая проверка из корня — `pnpm lint`, `pnpm test`, `pnpm build`, `pnpm typecheck`, `pnpm format:check`. Сквозные наборы запускаются через `pnpm test:integration` и требуют Docker. Они используют временные БД и изолированные очереди. Никогда не направляйте их на production DATABASE_URL. Это проверка функциональных гарантий, а не нагрузочный тест.
