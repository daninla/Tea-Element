# Проект на собеседовании

## Рассказ за минуту

«Я разработал Tea Element — интернет-магазин чая и посуды на Next.js и NestJS. В нем есть каталог, гостевая корзина, checkout, аккаунт, административное управление заказами и остатками. Бэкенд разделен на auth, catalog, orders, payments и marketing, у каждого своя PostgreSQL БД. Синхронные запросы и асинхронные события проходят через RabbitMQ.

Самая интересная часть — согласованность заказа, склада и оплаты. Я использовал Transactional Outbox, идемпотентные обработчики и локальные блокировки. Например, повтор OrderCreated не должен дважды резервировать чай, а поздняя оплата отмененного заказа требует компенсации. Для платежей есть интерфейс PaymentProvider и адаптер LiqPay Sandbox. При разработке проверял повторные запросы, отмены, потерянные callbacks и гонки на интеграционном стенде».

Уровень самостоятельности и использование AI описывайте честно. Будьте готовы открыть код, объяснить каждую ветку и изменить небольшой сценарий на месте. Опыт интеграционного теста не следует выдавать за опыт эксплуатации под реальной нагрузкой.

## Вопросы и ответы

### Почему микросервисы для небольшого магазина

Чтобы реализовать и изучить независимое владение данными, событийную согласованность и платежный workflow. Границы выделены по доменам. Для небольшого коммерческого MVP модульный монолит сократил бы инфраструктуру и число сетевых отказов. Выбор здесь имеет учебную и портфельную ценность; измеренной необходимости в таком разделении по нагрузке пока нет.

### Почему пять БД на одном сервере

Разделение владения данными не требует пяти физических PostgreSQL-инстансов. Отдельные БД и роли уменьшают связанность, один сервер экономит ресурсы. При этом сервер остается общей точкой отказа, а CPU, I/O и память разделяются.

### Зачем Outbox, если есть надежный RabbitMQ

Нужно атомарно связать локальную запись заказа и факт необходимости публикации. Без Outbox процесс может сохранить заказ, упасть до publish и потерять резервирование. Publisher confirms решает другую границу — подтверждение приема брокером. Падение после confirm до фиксации publishedAt все равно допускает дубликат.

### Можно ли гарантировать exactly once

Для всей сети, провайдера и SMTP такая гарантия здесь не дается. Используется повторяемая доставка и идемпотентный локальный эффект. Входящий event ID, бизнес-состояние и исходящий Outbox коммитятся вместе. Стабильный SMTP Message-ID помогает идентифицировать повтор, но не гарантирует единственное письмо в ящике.

### Чем idempotency key отличается от event ID

Первый связывает повтор HTTP-команды с ее содержимым. Второй идентифицирует доставленное событие. Одно бизнес-действие может прийти с разными event ID, поэтому нужны также уникальный резерв по order ID и проверка текущего перехода. Ключ с новым содержимым должен вызывать конфликт.

### Как не продать один остаток двум покупателям

Сервер собирает потребность всех вариантов одного продукта, блокирует inventory в стабильном порядке, проверяет свободный остаток и резервирует все позиции одной локальной транзакцией. Проверка inStock на карточке — подсказка. Окончательный результат резерва определяется catalog.

### Зачем блокировать в одном порядке

Если один процесс берет product A, затем B, а второй B, затем A, возможен deadlock. Стабильный порядок ID снижает этот риск. Нужны также bounded transaction time и обработка ошибок.

### Как работает saga

Orders фиксирует PENDING и OrderCreated. Catalog резервирует и возвращает событие. Orders подтверждает либо отклоняет. Отмена запускает освобождение резерва и при необходимости платежную компенсацию. У каждого шага локальная транзакция и повторяемый consumer, общей distributed transaction нет.

### Что будет, если отмена пришла раньше создания

Сохраняется tombstone. Поздний OrderCreated или PaymentRequested видит след отмены и не восстанавливает обычный workflow. Один только processed event ID не решает такую перестановку разных событий.

### Почему деньги в Int

Целые копейки дают точные операции и сравнения без погрешности двоичных floating point. На границе LiqPay значение превращается в десятичную строку. Диапазон суммы ограничен. Для процентной скидки используется целочисленное вычисление, поэтому порядок округления определен.

### Что является подтверждением оплаты

Проверенный webhook или status API провайдера, сверенный с merchant, попыткой, суммой и валютой. Result URL браузера не дает такого доказательства. Orders становится PAID после обработки события актуальной попытки.

### Что делать при потерянном webhook

Payments worker запрашивает статус у провайдера и пропускает результат через тот же observe/state machine. При timeout нельзя придумать успех. Если deadline уже привел к отмене, позднее реальное поступление требует компенсации.

### Зачем несколько попыток оплаты

Идентичность попытки позволяет различать поздний успех старой оплаты и успех текущей. Retry создает новый UUID, старый получает abandoned marker. Иначе два разных поступления легко ошибочно объединить в одно поле заказа.

### Какие возвраты реализованы

Техническая компенсация поздних и отмененных оплат и учет подтвержденных результатов провайдера. Обычный интерфейс возврата покупателем и создание частичных возвратов исключены владельцем. Неопределенный внешний результат переводится в REVIEW_REQUIRED.

### Где используется CQRS и event sourcing

Есть разделенные use cases чтения/записи и проекции verified identities и marketing purchases. Текущее состояние хранится в обычных таблицах. Event sourcing, при котором сущность целиком восстанавливается из журнала событий, не реализован.

### Есть ли Cache Aside

Redis-кэш каталога отсутствует. Есть React request memoization, TanStack Query, persisted cart и долговременный cache загруженных media. Перед добавлением Redis нужно выбрать ключи, TTL, инвалидацию и поведение при его отказе. Финальное решение о цене или платеже нельзя основывать только на устаревшем browser cache.

### Где слабые места масштабирования

Gateway rate limits пока process-local. Publisher делает сетевой вызов внутри БД-транзакции. Часть polling/report запросов потребует оценки на больших таблицах, некоторые списки используют pagination с растущей стоимостью смещения. Медиа лежат на локальном диске. При масштабировании понадобятся общий rate-limit storage, план медиа/object storage, метрики и нагрузочное измерение.

### Как обеспечена безопасность гостевых заказов

По номеру заказа доступ не выдается. Нужен длинный bearer token либо подтвержденный владелец аккаунта. В БД хранится hash токена. Совпадение email не привязывает заказ до подтверждения адреса. Приватные ссылки нельзя публиковать в логах или событиях.

### Как тестировать такой проект

Unit-тестами проверять правила и state machine. HTTP-тестами — роли, Origin и валидацию. Интеграционными наборами с реальными PostgreSQL/RabbitMQ — rollback Outbox, конкурирующие запросы, semantic duplicates, переставленные события, истечение резервов и SMTP. Sandbox acceptance у провайдера и нагрузочные тесты остаются отдельными этапами.

## Практика перед интервью

Откройте CreateOrder и проследите один запрос через gateway до catalog и Outbox. Затем найдите, какая транзакция сохраняет processedEvent. Покажите блокировку inventory и объясните единицы грамм/штук. В Payments найдите сравнение суммы, проверку подписи, выбор текущей попытки и поведение при lost callback. Наконец, найдите в actual schema уникальный индекс, который защищает повтор соответствующей команды.

Так вы сможете подкрепить рассказ конкретным кодом и объяснить, какое изменение потребуется при новых условиях.
