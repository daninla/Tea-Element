## 1. Суть проекта

**«Чайний елемент»** — интернет-магазин китайского чая. Бизнес-модель: владелец закупает чай оптом (килограммами) и продаёт его розницей порциями (25 г, 50 г, 100 г и т. д.).

**Главные цели:**
1. Рабочий магазин: каталог, корзина, оформление заказа.
2. Админ-панель, где владелец сам управляет товарами, остатками, акциями и заказами.
3. Автоматические email-рассылки на основе анализа покупок клиента.
4. Проект-портфолио: чистая микросервисная архитектура с понятными паттернами, которые можно объяснить на собеседовании.

**Ключевой принцип:** регистрация **никогда не блокирует покупку**. Весь пользовательский функционал (каталог, поиск, корзина) доступен без входа; данные покупателя и доставки запрашиваются **только на этапе оформления заказа**. Аккаунт — опция, дающая удобство (история, повтор заказа, автозаполнение).

**Роли:**
| Роль | Возможности |
|---|---|
| `CUSTOMER` | Просмотр каталога, корзина, заказы, профиль, история покупок, управление подпиской на рассылки |
| `ADMIN` | Всё, что у покупателя + админ-панель: товары, закупки/остатки, акции, заказы, клиенты, аналитика |
| Гость | Просмотр каталога, корзина (локально), **оформление и оплата заказа без регистрации**, отслеживание своего заказа по ссылке из письма, регистрация/вход |

## 2. Допущения (можно изменить)

- Язык интерфейса: **украинский** (в коде, комментариях, README — английский).
- Валюта: **UAH (₴)**.
- Доставка: «Нова пошта» (отделение / адрес) + самовывоз. На MVP — ручной ввод данных получателя и города/отделения без интеграции с API.
- Оплата (оба способа в MVP): **онлайн картой** через **LiqPay** (hosted checkout-страница провайдера, sandbox для разработки) и **оплата при получении**. Провайдер спрятан за интерфейсом `PaymentProvider` (паттерн Strategy) — WayForPay / Monobank Acquiring можно добавить позже без правки остального кода.
- Данные банковских карт **никогда** не попадают на наши серверы (оплата на стороне провайдера → минимальные требования PCI DSS, SAQ-A).
- Гостевой checkout: гость вводит имя, фамилию, телефон, email и данные доставки; аккаунт создаётся по желанию (в т. ч. одним кликом после заказа).
- Один владелец-админ (в системе может быть несколько ADMIN).

## 3. Технологический стек

### 3.1 Frontend (`apps/web`)
- **Next.js 15** (App Router) + **TypeScript** (strict)
- **Tailwind CSS** + **shadcn/ui** (компоненты) + **lucide-react** (иконки)
- **TanStack Query** — серверное состояние (запросы к API)
- **Zustand** — клиентское состояние (корзина гостя, UI)
- **React Hook Form + Zod** — формы и валидация
- **next-intl** — локализация (стартуем с `uk`, структура готова для `en`)
- **Recharts** — графики в админ-дашборде
- **next/font** (Inter + Cormorant Garamond или аналог) для типографики

### 3.2 Backend (`apps/*` — микросервисы)
- **NestJS** (monorepo mode), **TypeScript** (strict)
- **PostgreSQL 16** + **Prisma** (отдельная схема/БД на каждый сервис)
- **RabbitMQ** — брокер событий между сервисами (через `@nestjs/microservices`, транспорт RMQ)
- **Redis** — кэш каталога, rate limiting, blacklist refresh-токенов (опционально)
- **JWT** (`@nestjs/jwt`, `passport-jwt`), **argon2** — хэширование паролей
- **class-validator / class-transformer** — валидация DTO
- **Node `crypto`** — подпись запросов и проверка подписи webhook'ов платёжного провайдера (timing-safe сравнение)
- **@nestjs/swagger** — OpenAPI-документация
- **@nestjs/schedule** — cron-задачи
- **Nodemailer** + **React Email** или **Handlebars** — шаблоны писем; в dev — **Mailpit**
- **Pino** (`nestjs-pino`) — структурированные логи с correlation-id
- **Jest** + **Supertest** — тесты

### 3.3 Инфраструктура
- **Docker + docker-compose** (всё поднимается одной командой)
- **pnpm workspaces** + **Turborepo** (монорепозиторий)
- **ESLint + Prettier + Husky + lint-staged + Commitlint** (Conventional Commits)
- **GitHub Actions** — CI (lint, test, build)
- `.env.example` для каждого сервиса

### 4.2 Применяемые паттерны (для резюме и собеседования)

Это ключевая «объяснимая» часть проекта. Каждый паттерн должен быть реализован **явно** и описан в `docs/architecture/patterns.md` (что, зачем, как реализовано в коде, какие компромиссы).

| # | Паттерн | Где применяется | Что объяснить на собеседовании |
|---|---|---|---|
| 1 | **API Gateway** | `apps/gateway` | Единая точка входа, скрывает внутреннюю топологию, централизованные auth/rate-limit/логирование |
| 2 | **Database per Service** | Каждый сервис — своя БД/схема, чужие таблицы напрямую не читаются | Слабая связность, независимое развёртывание, цена — отсутствие JOIN между сервисами |
| 3 | **Event-Driven Architecture (Choreography)** | Взаимодействие через события RabbitMQ | Асинхронность, отсутствие жёстких зависимостей |
| 4 | **Saga (хореографическая)** | Оформление заказа: `OrderCreated` → резерв остатков в catalog (`StockReserved` / `StockReservationFailed`) → для онлайн-оплаты `PaymentRequested` → `PaymentSucceeded` / `PaymentFailed` / `PaymentExpired` → заказ оплачен или отменён с освобождением резерва | Распределённые транзакции без 2PC, компенсирующие действия (возврат остатков, возврат денег), таймауты саги |
| 5 | **Transactional Outbox** | В orders и catalog: событие записывается в таблицу `outbox` в той же транзакции, что и изменение данных; отдельный publisher отправляет в брокер | Гарантия «данные сохранены ⇔ событие отправлено», at-least-once доставка |
| 6 | **Idempotent Consumer** | Все обработчики событий (таблица `processed_events`) | Дубликаты сообщений не ломают состояние |
| 7 | **CQRS-lite** | marketing-service строит собственную read-модель покупательского профиля (`customer_profile`) из событий | Денормализованная модель, оптимизированная под чтение/аналитику |
| 8 | **Repository + Clean/Hexagonal layers** | Внутри каждого сервиса | Тестируемость, независимость домена от фреймворка |
| 9 | **Strategy** | `PaymentProvider` (LiqPay / Fake для тестов / далее Monobank), `EmailTemplateStrategy`, правила рассылок (`CampaignRule`) | Расширяемость без правки существующего кода |
| 10 | **Anti-Corruption Layer + Idempotent Webhook** | `payments-service`: адаптер провайдера переводит чужие статусы и формат в наши доменные события; webhook проверяется по подписи и обрабатывается идемпотентно | Изоляция внешнего API, защита от подделки и повторной доставки callback'ов |

> **Главный «герой» для резюме:** Saga (choreography) + Transactional Outbox + идемпотентные платёжные webhook'и. Именно на них строится заказ и оплата.

### 4.3 Сервисы и их ответственность

#### `gateway`
- Принимает все HTTP-запросы от фронтенда, валидирует JWT, проверяет роли (`RolesGuard`).
- Маршрутизирует запросы к сервисам (request-response через RMQ/TCP).
- Rate limiting (`@nestjs/throttler`), CORS, Helmet, Swagger (агрегированный).
- Различает три типа доступа: `@Public()` (каталог, гостевой checkout, webhook'и), `@Roles(CUSTOMER)` и `@Roles(ADMIN)`. Для гостевых заказов доступ к конкретному заказу — по одноразовому `accessToken` (см. раздел 7).
- **Не содержит бизнес-логики и не обращается к БД.**

#### `auth-service` (БД `auth_db`)
- Регистрация, логин, refresh, logout, смена пароля, сброс пароля по email.
- Хранит пользователей (`users`) и роли.
- Выдаёт access/refresh JWT. Публикует событие `UserRegistered`.

#### `catalog-service` (БД `catalog_db`)
- Категории, товары, варианты (порции), остатки в граммах, закупочные партии, акции.
- Резервирует/списывает остатки по событиям заказов.
- Публикует `StockReserved`, `StockReservationFailed`, `StockLow`, `PromotionStarted`.

#### `orders-service` (БД `orders_db`)
- Заказы **как авторизованных пользователей, так и гостей** (`user_id` nullable, контактные данные хранятся в самом заказе), позиции, статусы, история.
- Серверная корзина — только для авторизованных (гостевая живёт в браузере и передаётся при оформлении). **Цены и скидки при создании заказа всегда пересчитываются на сервере** — данным клиента не доверяем.
- Генерирует `accessToken` для гостевого заказа (хранится хэш) и ссылку на отслеживание.
- Привязывает прошлые гостевые заказы к аккаунту по подтверждённому email (событие `UserEmailVerified`).
- Реагирует на события склада и платежей (хореографическая сага), по таймауту отменяет неоплаченные заказы.
- Публикует `OrderCreated`, `PaymentRequested`, `OrderConfirmed`, `OrderPaid`, `OrderCancelled`, `OrderCompleted`.

#### `marketing-service` (БД `marketing_db`)
- Слушает события (`UserRegistered`, `OrderCompleted`, `PromotionStarted`), строит профиль клиента. **Профиль ключуется по email**, поэтому анализ и рассылки работают и для гостевых покупателей (при наличии согласия).
- Анализ покупок, правила кампаний, cron-планировщик, отправка писем, лог отправок, отписки.
- (Внутри модуль `mailer`; при росте проекта можно выделить в `notification-service`.)

#### `payments-service` (БД `payments_db`)
- Единственный сервис, знающий о платёжном провайдере. Интерфейс `PaymentProvider { createCheckout(), verifyWebhook(), parseWebhook(), getStatus(), refund() }`; реализации `LiqPayProvider`, `FakePaymentProvider` (для тестов и dev-режима без интернета).
- Слушает `PaymentRequested` → создаёт платёж (`CREATED`), хранит сумму и заказ.
- Отдаёт данные для редиректа на оплату (для LiqPay — `data` + `signature` + `actionUrl`).
- Принимает webhook провайдера: **проверка подписи → идемпотентная обработка → обновление статуса → событие** (`PaymentSucceeded` / `PaymentFailed`).
- Фоновая сверка: cron опрашивает провайдера по «зависшим» платежам (если webhook не пришёл) — `getStatus()`.
- Таймаут неоплаченного платежа (по умолчанию 30 минут) → `PaymentExpired`.
- Возвраты: по `OrderCancelled` для оплаченного заказа (или вручную из админки) → `refund()` → `PaymentRefunded`.
- Публикует `PaymentSucceeded`, `PaymentFailed`, `PaymentExpired`, `PaymentRefunded`.

### 4.4 Структура каждого NestJS-сервиса (Clean/Hexagonal)

```
apps/<service>/src/
├── main.ts
├── app.module.ts
├── config/                     # типизированная конфигурация (env + Zod-валидация)
├── modules/
│   └── <feature>/
│       ├── domain/             # сущности, value objects, доменные события, интерфейсы репозиториев
│       ├── application/        # use-cases / command & query handlers, DTO сервисного уровня
│       ├── infrastructure/     # Prisma-репозитории, клиенты брокера, внешние API
│       ├── presentation/       # контроллеры, message/event-handlers, DTO запросов
│       └── <feature>.module.ts
├── shared/                     # кросс-срезовое: фильтры исключений, интерсепторы, outbox, idempotency
└── prisma/
    ├── schema.prisma
    └── migrations/
```

Правила зависимостей: `presentation → application → domain`; `infrastructure → domain`. **Домен ничего не знает о NestJS и Prisma.**

## 6. Доменная модель и БД (PostgreSQL)

Один инстанс PostgreSQL, **отдельная БД на сервис**. Ниже — логические сущности (полные схемы пишутся в `schema.prisma` каждого сервиса). Первичные ключи — `uuid`, у всех таблиц `created_at`, `updated_at`.

### 6.1 auth_db
- `users` — id, email (unique), password_hash, first_name, last_name, phone, role (`CUSTOMER`|`ADMIN`), is_active, email_verified_at, default_delivery (jsonb — сохранённые данные доставки для автозаполнения checkout)
- `refresh_tokens` — id, user_id, token_hash, expires_at, revoked_at, user_agent, ip
- `password_reset_tokens` — id, user_id, token_hash, expires_at, used_at
- `outbox`, `processed_events`

### 6.2 catalog_db
- `categories` — id, slug, name, description, sort_order (напр. Пуэр, Улун, Зелёный, Красный, Белый, Габа, Травяной/Тизан)
- `products` — id, slug, name, name_original (китайское название), description, origin (провинция/регион), year, brewing_guide (температура, время, количество проливов), category_id, images[], is_active, tags[]
- `product_variants` — id, product_id, weight_grams (25/50/100/200…), price (в копейках, int), sku, is_active
- `inventory` — product_id, stock_grams (остаток **в граммах** — общий для всех порций товара), reserved_grams, low_stock_threshold_grams
- `purchase_batches` — id, product_id, supplier, weight_grams, purchase_price_total, purchased_at, note *(закупки опта — для учёта себестоимости и пополнения остатков)*
- `stock_movements` — id, product_id, type (`PURCHASE`|`SALE`|`RESERVE`|`RELEASE`|`WRITE_OFF`|`ADJUSTMENT`), grams, ref_id, created_at *(журнал движения остатков)*
- `promotions` — id, name, type (`PERCENT`|`FIXED`), value, starts_at, ends_at, is_active
- `promotion_targets` — promotion_id, product_id | category_id *(акция на товар или на категорию)*
- `outbox`, `processed_events`

> **Ключевая бизнес-логика:** продажа порции 50 г списывает 50 г с `inventory.stock_grams`. Цена варианта в момент заказа фиксируется в заказе (snapshot).

### 6.3 orders_db
- `carts`, `cart_items` — серверная корзина **только авторизованного** пользователя
- `orders` — id, number (человекочитаемый), **user_id (nullable — NULL для гостя)**, status, total_amount, discount_amount, delivery_method, delivery_address (jsonb: город, отделение «Нової пошти»/адрес, индекс), **customer_first_name, customer_last_name, customer_phone, customer_email** (snapshot контактов на момент заказа), payment_method (`ONLINE_CARD`|`CASH_ON_DELIVERY`), payment_status (`UNPAID`|`PAID`|`REFUNDED`|`FAILED`), payment_expires_at, **access_token_hash** (доступ гостя к заказу), marketing_consent_at, comment
- `order_items` — order_id, product_id, variant_id, product_name_snapshot, weight_grams, unit_price_snapshot, quantity
- `order_status_history` — order_id, from_status, to_status, changed_by, created_at
- `outbox`, `processed_events`

**Статусы заказа:**
- Оплата при получении: `PENDING` → `CONFIRMED` (остатки зарезервированы) → `SHIPPED` → `COMPLETED`.
- Онлайн-оплата: `PENDING` → `AWAITING_PAYMENT` (остатки зарезервированы, ждём оплату) → `PAID` → `SHIPPED` → `COMPLETED`.
- Исключения: `REJECTED` (нет остатков), `CANCELLED` (отмена, неоплата в срок, ошибка оплаты; резерв освобождается, при необходимости делается возврат денег).

### 6.4 marketing_db
- `customer_profiles` — id, **email (unique, ключ профиля)**, user_id (nullable — заполняется, если клиент зарегистрирован), first_name, registered_at, last_order_at, orders_count, total_spent, avg_order_interval_days, favorite_category_ids[], marketing_consent (bool), unsubscribed_at
- `customer_purchase_stats` — profile_id, product_id, category_id, purchases_count, last_purchased_at *(read-модель из событий)*
- `campaigns` — id, type, name, is_active, config (jsonb)
- `email_logs` — id, profile_id, campaign_type, subject, status (`SENT`|`FAILED`|`SKIPPED`), sent_at, error
- `unsubscribe_tokens` — profile_id, token
- `processed_events`

### 6.5 payments_db
- `payments` — id, order_id, order_number, amount (копейки), currency (`UAH`), provider (`LIQPAY`|`FAKE`), provider_payment_id, status (`CREATED`|`PENDING`|`SUCCEEDED`|`FAILED`|`EXPIRED`|`REFUNDED`|`PARTIALLY_REFUNDED`), failure_reason, paid_at, expires_at
- `payment_events` — id, payment_id, provider_event_id, raw_payload (jsonb), signature_valid (bool), received_at *(журнал **всех** сырых webhook'ов для аудита и разбора спорных ситуаций)*
- `refunds` — id, payment_id, amount, status, reason, created_by
- `outbox`, `processed_events`

> Суммы везде хранятся **целыми числами в копейках** (никаких float).

## 7. Аутентификация и авторизация (JWT)

- **Access token**: JWT, TTL 15 мин, payload `{ sub, email, role }`.
- **Refresh token**: JWT/opaque, TTL 7 дней, хранится в БД **в виде хэша**, **ротация при каждом refresh** (старый отзывается; повторное использование отозванного → отзыв всей цепочки).
- Токены передаются в **httpOnly + Secure + SameSite=Lax cookies** (защита от XSS); CSRF-защита через SameSite + проверка Origin.
- Пароли — **argon2id**. Политика: минимум 8 символов.
- Проверка JWT и ролей — **в gateway** (`JwtAuthGuard`, `RolesGuard`, декоратор `@Roles(Role.ADMIN)`, `@Public()`); во внутренние сервисы передаётся доверенный контекст пользователя (`userId`, `role`) в метаданных сообщения.
- Next.js: `middleware.ts` защищает маршруты `/account/*` (любой авторизованный) и `/admin/*` (только `ADMIN`).
- Эндпоинты: `POST /auth/register`, `/auth/login`, `/auth/refresh`, `/auth/logout`, `/auth/forgot-password`, `/auth/reset-password`, `GET /auth/me`.
- Первый админ создаётся seed-скриптом (`pnpm seed:admin`) из переменных окружения.
- Rate limit на `/auth/*` (защита от перебора).
- Эндпоинт `POST /auth/verify-email` + письмо с подтверждением email.

**Гостевой режим:**
- Гость не получает JWT. Публичные эндпоинты: каталог, `POST /orders/guest`, `POST /payments/checkout`, `GET /orders/:number?token=…`, webhook'и.
- При создании гостевого заказа генерируется случайный `accessToken` (≥ 32 байта). В БД — только хэш. Токен приходит в письме (ссылка `/order/{number}?token=…`) и показывается на странице «Дякуємо». По нему гость видит статус заказа и может повторно перейти к оплате.
- Дополнительно — форма «Знайти замовлення»: номер заказа + email (с rate limit, без раскрытия, существует ли заказ).
- **Регистрация одним кликом после заказа:** `POST /auth/register-from-order` (`orderNumber`, `token`, `password`) — email и имя берутся из заказа, пользователю нужно придумать только пароль.
- **Привязка истории:** после подтверждения email (`UserEmailVerified`) все гостевые заказы с таким email привязываются к аккаунту. Без подтверждения email привязка запрещена (защита от чужого доступа к истории).
- Если гость вводит email, уже зарегистрированный в системе, заказ всё равно оформляется как гостевой; в UI мягко предлагается войти (без раскрытия лишних данных).
- Middleware Next.js: `/checkout`, `/cart`, `/order/*` — доступны всем; `/account/*` — только авторизованным; `/admin/*` — только `ADMIN`.

### 8.3 Email-маркетинг на основе анализа покупок

**Принцип:** `marketing-service` по событиям поддерживает профиль клиента, а cron-задача раз в сутки применяет **правила кампаний** (паттерн Strategy: интерфейс `CampaignRule { id, isApplicable(profile), buildEmail(profile) }`).

**Письма:**
| Тип | Триггер | Содержание |
|---|---|---|
| Welcome | `UserRegistered` | Приветствие, промокод/подборка для новичков |
| Підтвердження замовлення | `OrderConfirmed` / `OrderPaid` | Транзакционное, содержит ссылку на отслеживание заказа (для гостя — с токеном); отправляется независимо от согласия на маркетинг |
| Нагадування про неоплачений заказ | `AWAITING_PAYMENT` > 15 мин, не истёк | Транзакционное напоминание со ссылкой на оплату (один раз) |
| Win-back («давно не купував») | N дней без покупок (по умолчанию = 1.5 × средний интервал между заказами клиента, но не меньше 30 дней) | Напоминание + персональная подборка из его любимой категории |
| Персональная акция | `PromotionStarted` по категории/товару, который клиент покупал | «Чай, який ви любите, зараз зі знижкою» |
| Закончился/пора повторить | Расчёт: купил 50 г → ориентировочно хватит на X дней | «Час поповнити запаси» |
| Новинка в любимой категории | Добавлен новый товар в категорию из `favorite_category_ids` | Анонс (с лимитом частоты) |

**Ограничения и этика (обязательно):**
- Маркетинговые письма отправляются только при `marketing_consent = true`; согласие — чекбокс при регистрации и **при оформлении заказа** (не предустановлен, в том числе для гостей) и в кабинете. Для гостя профиль создаётся по email из заказа; без согласия данные используются только для транзакционных писем.
- В каждом письме — **ссылка «Відписатися»** (одним кликом, по токену).
- **Частота:** не более 1 маркетингового письма в 7 дней на пользователя (глобальный лимит); дедупликация одной и той же кампании.
- Все отправки пишутся в `email_logs`; ошибки — ретраи (3 попытки, экспоненциальная задержка).
- Транзакционные письма: подтверждение заказа, успешная оплата, возврат средств, смена статуса, сброс пароля, подтверждение email.
- Шаблоны писем — в одном месте, в стиле сайта, адаптивные.
- В dev-окружении письма уходят в **Mailpit** (http://localhost:8025).

## 9. Нефункциональные требования

- **Безопасность:** OWASP Top-10; валидация всех входных данных (DTO + Zod); Helmet; CORS-whitelist; параметризованные запросы (Prisma); секреты только в env; никаких паролей/токенов в логах.
- **Платежи:** карточные данные не обрабатываются и не хранятся; webhook проверяется по подписи (timing-safe) и обрабатывается идемпотентно; сумма оплаты сверяется с суммой заказа; все сырые callback'и логируются в `payment_events`; секретные ключи провайдера — только в env; сумма и состав заказа никогда не берутся из данных клиента.
- **Производительность:** кэш каталога в Redis (инвалидация по событиям), пагинация везде, индексы по `slug`, `category_id`, `user_id`, `created_at`; изображения через `next/image`.
- **Надёжность:** health-check эндпоинты (`/health`) у каждого сервиса; graceful shutdown; ретраи и DLQ (dead letter queue) в RabbitMQ.
- **Наблюдаемость:** структурированные логи с `correlationId`, проходящим через все сервисы и события.
- **Тестирование:** unit-тесты use-cases (домен/приложение), e2e-тесты критических сценариев (регистрация → заказ → списание остатка), тест идемпотентности обработчиков и сценария компенсации саги. Целевое покрытие use-cases ≥ 70%.
- **Качество кода:** линтер без ошибок, строгий TS, никаких `any` без комментария, Conventional Commits.
- **Документация:** Swagger для API, README в каждом приложении, `docs/architecture/*`.

## 12. Правила для AI-ассистентов (содержимое `AGENTS.md`)

Создать в корне `AGENTS.md` со следующими правилами — чтобы любая нейросеть/разработчик без контекста мог продолжать работу:

1. **Сначала читай:** `SPEC.md`, `docs/architecture/overview.md`, README нужного приложения.
2. **Где что лежит:** карта репозитория (раздел 5) и структура сервиса (раздел 4.4) — не нарушать.
3. **Новая фича = новый модуль** по шаблону `domain / application / infrastructure / presentation`. Не класть бизнес-логику в контроллеры.
4. **Межсервисное взаимодействие только через** `packages/contracts` (события/DTO). Не импортировать код одного сервиса в другой. Не обращаться к чужой БД.
5. **Любое изменение состояния + публикация события = через Outbox.** Любой обработчик события = идемпотентный.
6. **Новое событие:** добавить тип в `packages/contracts`, описать в `docs/architecture/events.md`.
7. **Миграции БД:** только через Prisma Migrate, никаких ручных правок схемы.
8. **Не добавлять зависимости** без необходимости; если добавляешь — объясни в PR/ADR.
9. **После изменений:** запустить `pnpm lint && pnpm test && pnpm build`.
10. **Не оставлять TODO без тикета** и не писать «заглушки», маскирующиеся под рабочий код.
11. Значимое архитектурное решение → новый файл в `docs/adr/`.
12. Именование: файлы `kebab-case`, классы `PascalCase`, события `PascalCase` в прошедшем времени (`OrderCreated`), очереди `service.event_name`.
13. **Платежи:** вся работа с провайдером — только в `payments-service` через интерфейс `PaymentProvider`. Webhook без валидной подписи отклоняется. Любой переход статуса платежа идемпотентен. В логи не пишутся ключи и платёжные данные.
14. **Гости:** любой код, работающий с заказом, учитывает `user_id = null`. Доступ гостя к заказу — только по `accessToken`; никогда не отдавать данные заказа по одному лишь номеру.
15. Цены, скидки и суммы **всегда** считаются на сервере; деньги — целые числа в копейках.

- `pnpm db:migrate` — миграции всех сервисов; `pnpm db:seed` — демо-данные (10–15 чаёв с реальными названиями, категории, 2 акции, admin-пользователь, тестовые заказы для аналитики).
- Платежи в dev: по умолчанию `PAYMENT_PROVIDER=fake` (эмулятор: страница «успех/ошибка» + имитация webhook'а); для проверки LiqPay sandbox — `PAYMENT_PROVIDER=liqpay` и ключи `LIQPAY_PUBLIC_KEY` / `LIQPAY_PRIVATE_KEY` из `.env`, публичный URL для webhook через `cloudflared`/`ngrok`.
- Порты: web `3000`, gateway `4000`, сервисы — внутри docker-сети.
- Swagger: `http://localhost:4000/docs`.

## 15. Критерии приёмки MVP

- [ ] Покупатель может зарегистрироваться, найти чай, выбрать порцию, оформить заказ и увидеть его в кабинете.
- [ ] Остаток в граммах корректно уменьшается после заказа и возвращается при отмене.
- [ ] При одновременном заказе последнего остатка двумя пользователями только один успешен (нет oversell).
- [ ] Админ может: добавить товар, внести закупку, поставить акцию (цены на витрине меняются), сменить статус заказа, увидеть дашборд.
- [ ] Роли работают: CUSTOMER не получает доступ к `/admin` ни в UI, ни в API (проверено тестом).
- [ ] Если marketing-service остановлен, заказы продолжают оформляться; после запуска события дообрабатываются (устойчивость).
- [ ] Win-back и промо-письма формируются по правилам и приходят в Mailpit; в каждом есть отписка; частота ограничена.
- [ ] Повторная доставка одного и того же события не создаёт дубликатов (тест идемпотентности).
- [ ] `docs/architecture/patterns.md` описывает каждый паттерн из раздела 4.2 с указанием файлов в коде.
- [ ] **Гость может оформить заказ без регистрации**, введя контакты и данные доставки; получает письмо со ссылкой на отслеживание заказа.
- [ ] Гость не может открыть чужой заказ (нет доступа без валидного токена; проверено тестом).
- [ ] После регистрации (с подтверждённым email) прошлые гостевые заказы появляются в кабинете.
- [ ] Онлайн-оплата в sandbox: успех → заказ `PAID`; отказ → заказ можно оплатить повторно или сменить способ; неоплата за 30 минут → заказ `CANCELLED`, остатки освобождены.
- [ ] Webhook с неверной подписью отклоняется; повторный валидный webhook не создаёт дублей (тесты).
- [ ] Если webhook потерялся, фоновая сверка всё равно приводит платёж в корректный статус.
- [ ] Отмена оплаченного заказа админом запускает возврат средств.
- [ ] Проект запускается с нуля по README за ≤ 5 команд.
- [ ] Lint, тесты и сборка проходят в CI.

## 16. Как это рассказывать на собеседовании (шпаргалка)

> «Я разработал интернет-магазин на Next.js и NestJS с микросервисной архитектурой: API Gateway, четыре сервиса с отдельными БД PostgreSQL и общение через RabbitMQ. Оформление заказа реализовано как **хореографическая сага** с компенсацией (резервирование остатков в catalog-service), надёжность публикации событий обеспечена паттерном **Transactional Outbox**, а обработчики — **идемпотентны**. Для email-маркетинга я построил **read-модель профиля клиента** (CQRS-lite), на основе которой cron-задача применяет правила кампаний (паттерн Strategy) — например, напоминание о давно не совершавшихся покупках. Оплата вынесена в отдельный `payments-service` с адаптером провайдера (Strategy + Anti-Corruption Layer): webhook'и проверяются по подписи и обрабатываются идемпотентно, зависшие платежи досверяются фоновой задачей, а неоплаченный заказ автоматически отменяется по таймауту саги. Авторизация — JWT с ротацией refresh-токенов и RBAC на уровне gateway; при этом покупка возможна и без регистрации — гостевой доступ к заказу защищён одноразовым токеном.»

**Вопросы, к которым стоит быть готовым:** почему микросервисы, а не монолит для такого масштаба (честный ответ: учебно-демонстрационная цель + компромиссы); что будет при падении брокера/сервиса; как избежать oversell; почему Outbox, а не просто publish после commit; как обеспечить консистентность без распределённых транзакций; как масштабировать каждый сервис; что произойдёт, если клиент оплатил, а webhook не дошёл; как защититься от поддельного webhook'а и от подмены суммы; как вы связываете гостевые заказы с аккаунтом и почему только после подтверждения email.
