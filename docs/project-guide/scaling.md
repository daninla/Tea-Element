# Оптимизация, репликация и шардирование

В проекте уже применены локальные блокировки, индексы, ограничения batch, request memoization и повторное использование соединений. Реплики PostgreSQL, table partitioning и routing по shards здесь ещё не настроены. Последующие разделы объясняют, как они повлияли бы на Tea Element и какие гарантии пришлось бы сохранить.

## Похожие термины решают разные задачи

| Механизм                     | Как меняет систему                                                 | Состояние Tea Element                                                                |
| ---------------------------- | ------------------------------------------------------------------ | ------------------------------------------------------------------------------------ |
| Вертикальное масштабирование | Больше CPU/RAM/I/O у одного узла                                   | Размер узла определяется окружением                                                  |
| Реплики приложения           | Несколько процессов одного сервиса                                 | Код имеет часть необходимых locks/leases, сквозная production-приемка нужна отдельно |
| Database per Service         | Данные разделены по ответственности                                | Реализовано пять БД на одном PostgreSQL-инстансе локально                            |
| Read replica                 | Копия данных для чтения и возможного failover                      | Не настроена                                                                         |
| Partitioning                 | Одна логическая таблица состоит из физических partitions           | Не настроен                                                                          |
| Sharding                     | Записи одной области данных распределены между независимыми узлами | Не настроен                                                                          |

Пять БД сервисов сами по себе не означают шардирование заказов. При шардировании orders_db могла бы быть разделена на несколько узлов по ключу, а не просто находиться отдельно от auth_db.

## С чего начинать оптимизацию

Сначала измерить конкретный путь. Например, checkout включает браузерный запрос, gateway, RPC orders, RPC catalog, SQL, внешнюю доставку и обратные ответы. Если большую часть времени занимает перевозчик, добавление индекса к users не ускорит выбор отделения.

Нужны latency p50/p95/p99 для маршрутов, число ошибок/таймаутов, время SQL и ожидания locks, pool saturation, глубина и возраст сообщений, длительность workers. В текущем проекте structured logs и correlation ID дают основу трассировки; завершенный distributed tracing и измеренные SLA не заявлены.

Число запросов в секунду допустимо обещать после нагрузочного теста на конкретном окружении. Интеграционные тесты конкуренции доказывают отдельные свойства корректности и не задают максимальную производительность.

## Уже примененные приемы

### Складская запись проверяет инвариант в SQL

[Ключевой файл и строка 139](../../apps/catalog-service/src/modules/stock/infrastructure/prisma-stock-store.ts#L139)

```ts
const changed = await tx.inventory.updateMany({
  where: {
    productId: item.productId,
    ...(item.unit === 'PIECE'
      ? { stockPieces: { gte: item.amount }, reservedPieces: { gte: item.amount } }
      : { stockGrams: { gte: item.amount }, reservedGrams: { gte: item.amount } }),
  },
  data:
    item.unit === 'PIECE'
      ? {
          stockPieces: { decrement: item.amount },
          reservedPieces: { decrement: item.amount },
        }
      : {
          stockGrams: { decrement: item.amount },
          reservedGrams: { decrement: item.amount },
        },
});
```

Этот фрагмент относится к списанию при отгрузке. Условия gte проверяются в том же statement, который уменьшает stock и reserved. Если строка не обновилась, последующий код проверяет changed.count и отклоняет операцию. Это закрывает окно между отдельным чтением и записью.

Проверка границ на frontend не защищает PostgreSQL от конкурирующего consumer или второго администратора. В местах резервирования используются транзакция, locks и вычисление полной потребности вариантов продукта. Смотрите [PrismaStockStore](../../apps/catalog-service/src/modules/stock/infrastructure/prisma-stock-store.ts).

### SKIP LOCKED и leases

[OutboxPublisher](../../apps/orders-service/src/shared/outbox/outbox-publisher.ts) пропускает записи, которые уже держит другая транзакция. [Очередь уведомлений](../../apps/orders-service/src/modules/notifications/infrastructure/prisma-payment-notice-store.ts) фиксирует leaseId и leaseUntil, чтобы следующая попытка могла восстановиться после падения worker.

SKIP LOCKED подходит для разделения очереди работ. Он пропускает занятые строки, поэтому результат не является полным согласованным списком всех ожидающих задач. Для пользовательского отчета нужна другая семантика чтения. Long-running задача требует разумного lease и проверки владельца при finish, иначе запоздалый worker может подтвердить чужую попытку.

### Ограниченные batch

SMTP worker ограничивает batch десятью задачами. Платежный due выбирает ограниченное число попыток. Ограничение снижает время одного прохода и давление на БД, но при большом backlog надо измерять, успевает ли обработчик за входящим потоком. Слишком маленький batch увеличивает задержку очереди даже при свободных ресурсах.

### Индексы и точечная выборка

Для истории пользователя полезен индекс по userId и createdAt. Для background queue — status и время следующей попытки. Prisma select/include определяет, сколько данных подтягивается. Для тяжелого ответа нужно проверять и число SQL-запросов, и объем возвращенных JSON.

Пример диагностического чтения для отдельного тестового orders_db приведен ниже. UUID заменяется существующим тестовым user ID. EXPLAIN ANALYZE действительно выполняет SELECT.

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, number, status, created_at
FROM orders
WHERE user_id = '00000000-0000-4000-8000-000000000001'
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

Смотрите выбранный scan, sort, actual rows, buffers и время. Индекс из schema не гарантирует отсутствие сортировки по дополнительному id. Выбор нового индекса обосновывается планом, статистикой и стоимостью записи. На маленькой таблице последовательное чтение может быть выгоднее index scan.

### Соединения и число процессов

Каждый PrismaService владеет своим клиентом и pool. Если поднять десять replicas пяти сервисов, общий бюджет соединений растет. Нужны расчет лимитов PostgreSQL и настройка pool/прокси при необходимости. Добавлять replicas приложения при уже исчерпанной БД может ухудшить latency.

### Дедупликация запросов и текущие кэши

В [server-catalog](../../apps/web/src/lib/api/server-catalog.ts) React cache сокращает повторные вызовы в одном серверном рендере. TanStack Query переиспользует данные браузерного запроса в заданном окне. Zustand сохраняет корзину, а сервер заново проверяет цену перед заказом.

Redis Cache Aside можно добавить к публичному каталогу после определения TTL, ключей и invalidation. Например, ключ должен учитывать section, category, sort, page и фильтры, а не только pathname. При массовой потере cache могут одновременно пойти одинаковые SQL-запросы; полезны single-flight и распределенный jitter TTL. Это возможное развитие, текущий backend такого Redis-кэша не содержит.

## Pagination для большого числа заказов

OFFSET легко реализовать для страницы с номером, но глубина пропуска увеличивает работу БД. Cursor pagination использует последнюю пару createdAt/id и индекс с совместимым порядком. Условный запрос для отдельного тестового окружения показан ниже; placeholders передаются как параметры через SQL-клиент.

```sql
SELECT id, number, created_at
FROM orders
WHERE user_id = $1
  AND (created_at, id) < ($2, $3)
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

Такой переход потребует изменить API и UI: произвольный переход к номеру страницы уже нельзя получить из одного cursor. Нужно определить стабильность сортировки, поведение при вставках и contract следующей страницы. Это предложение по развитию списка, существующие endpoints не переписаны под данный пример.

## Репликация PostgreSQL

Primary принимает запись, standby получает изменения и может обслуживать read-only запросы. В streaming replication переносится поток WAL. Async replica может отставать. Синхронный режим может ждать подтверждения standby; уровень ожидания зависит от настройки, а задержка сети влияет на commit. Для чтения примененных изменений важна разница между доставкой WAL и его replay. [Репликация PostgreSQL](https://www.postgresql.org/docs/current/warm-standby.html).

### Какие чтения можно перенести

Исторический отчет админки и часть каталога могут допускать задержку. Финальная проверка свободного склада, ротация refresh, проверка idempotency key и решение о текущей оплате должны опираться на авторитетное состояние. В рамках локальной write-транзакции использовать данные со standby нельзя.

Сценарий проблемы с read-after-write: покупатель создал заказ на primary, а следующий GET ушел на отстающую реплику. Пользователь увидит отсутствие заказа или старый статус. Применимый вариант — удерживать критические чтения на primary или маршрутизировать чтение на реплику только после подтверждения нужной позиции replay. Это проектное решение, которое еще нужно реализовать и проверить.

### Реплика для отказа узла

Для failover требуется выбрать новый primary и исключить одновременную запись в старый узел. Нужны orchestration, fencing, наблюдение lag и план reconnect клиентов. Настроенная standby сама по себе не реализует весь этот процесс. Async failover может потерять последние неподтвержденные репликой commits, что особенно важно для платежного ledger и idempotency.

Read-only standby имеет собственные ограничения запросов и конфликтов с восстановлением. Приложение должно обрабатывать отмену конфликтующего длинного чтения. Advisory locks на разных узлах не становятся общей распределенной блокировкой. [Hot standby](https://www.postgresql.org/docs/current/hot-standby.html).

Резервные копии нужны отдельно: удаление или поврежденное бизнес-изменение может реплицироваться вместе с остальными записями. План backup/point-in-time recovery определяется отдельно и тестируется восстановлением.

## Partitioning таблиц

Если payment_events, stock_movements или email_logs вырастут за годы эксплуатации, range partitioning по времени может упростить обслуживание и удаление старых периодов. Planner может исключить partitions по условиям запроса — partition pruning. При этом запрос без подходящего условия времени не обязательно станет быстрее.

Для уникальных ограничений partitioned table PostgreSQL накладывает требования к включению partition key. Поэтому разделение по createdAt может потребовать изменить нынешнюю глобальную уникальность eventId или dedupeKey. Такая миграция затрагивает корректность повторов и требует отдельного проектирования. [Table partitioning](https://www.postgresql.org/docs/current/ddl-partitioning.html).

Partitioning в одном PostgreSQL не устраняет предел CPU/I/O одного сервера автоматически. Миграцию нужно планировать с учетом существующих FK, объема данных, routing inserts и Prisma Migrate. Ниже показана только концептуальная форма для новой учебной таблицы, не команда изменения текущей payments.payment_events.

```sql
CREATE TABLE payment_events_learning (
  id uuid NOT NULL,
  created_at timestamptz NOT NULL,
  outcome text NOT NULL,
  PRIMARY KEY (created_at, id)
) PARTITION BY RANGE (created_at);
```

Заметьте, PK теперь содержит created_at. Это меняет смысл уникальности UUID по сравнению с одиночным primary key id и должно быть осознанным решением.

## Шардирование заказов

При sharding разные узлы хранят разные строки одной предметной области. Вариант `shard = hash(orderId) % N` прост для чтения заказа по ID, но не решает выборку всей истории пользователя или поиск по email. Каждое такое действие может потребовать fan-out или отдельной проекции. Это пример возможной схемы, а не текущая реализация.

### Как выбирать ключ

| Ключ                   | Удобный путь                        | Что усложняется                                                            |
| ---------------------- | ----------------------------------- | -------------------------------------------------------------------------- |
| orderId                | Получение и изменение одного заказа | История пользователя и guest email lookup                                  |
| userId                 | История аккаунта на одном shard     | Гостевые заказы с nullable userId и последующая привязка                   |
| tenantId               | Изоляция разных магазинов           | Проект сейчас обслуживает один магазин; крупный tenant может стать hotspot |
| productId для каталога | Один владелец запаса продукта       | Смешанная корзина затрагивает несколько shards                             |

Email плохо подходит как неосмысленный универсальный ключ: это персональные данные, он может измениться, а аккаунт и гость имеют разные правила идентификации. Изменение N при modulo routing может переместить значительную часть записей. Нужны shard map, версии маршрутизации и управляемая миграция данных либо иной алгоритм размещения.

### Что сломается при прямом переносе текущего кода

1. Уникальный idempotencyHash действует внутри одной БД. Если повтор команды попадает на другой shard, можно получить два заказа. Маршрутизация повторов должна быть детерминированной еще до создания нового случайного order ID.
2. Advisory lock защищает только выбранный PostgreSQL. Операции одного заказа нужно всегда направлять на один авторитетный shard.
3. Outbox должен остаться рядом с бизнес-записью в той же локальной транзакции. Общая отдельная БД Outbox вернет проблему двойной записи.
4. processed_events и semantic markers должны находиться там же, где применяется эффект. Глобальный брокер не делает две БД атомарными.
5. Административные totals и search требуют агрегирования по shards либо отдельной read model.
6. Изменение структуры усложнит backup/restore, миграции, наблюдаемость и перенос hot shards.

### Самая сложная граница — остатки

Если продукты одной корзины распределить между независимыми catalog shards, нынешняя локальная транзакция всего резерва больше не охватывает все позиции. Понадобится отдельный протокол частичных резервов, подтверждения и компенсаций. До его завершения заказ не должен считаться полностью зарезервированным.

Крупный спрос на один товар все равно будет конкурировать за его авторитетный stock. Простое добавление shards не уберет serialization по этому остатку. Сначала нужно измерить реальную горячую точку и решить, требуются ли изменения модели запасов.

## Практический план развития Tea Element

| Когда возникает проблема                       | Первое действие                   | Что проверяется перед следующим шагом                     |
| ---------------------------------------------- | --------------------------------- | --------------------------------------------------------- |
| Медленно открывается каталог                   | Разделить время API, SQL и SSR    | Query plan, payload, количество round trips               |
| Очередь растет при свободной БД                | Измерить handler time и prefetch  | Число consumers и безопасная идемпотентность              |
| Насыщены соединения БД                         | Посчитать pools всех процессов    | Размер pool, очередность запросов, proxy                  |
| Частые дорогие публичные чтения                | Спроектировать TTL и invalidation | Устаревшие цены и восстановление cache                    |
| Аналитика мешает checkout                      | Ограничить/оптимизировать запросы | Затем оценить replica для допустимых read paths           |
| Трудно обслуживать большой журнал              | Retention и индексы               | Затем partitioning с сохранением dedupe                   |
| Одного write-узла недостаточно после измерений | Оценить hotspots и границы записи | Затем shard key, миграции и новые транзакционные гарантии |

Для текущего размера проекта sharding остается учебной темой. Уже сейчас полезнее уметь объяснить locks, очереди, idempotency, read-after-write и план измерений. Все варианты масштабирования выше требуют отдельных изменений и проверки; добавление этой главы их не включает в приложение.
